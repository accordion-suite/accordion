# 23. Sync

- **Status:** Accepted
- **Date:** November 5, 2026

## Context

The spec promises "a desktop sync client (Windows, macOS, Linux) with selective sync and on-demand files", a Drive tab in the mobile app, and clients that "keep an offline copy and sync when they can reach" the server. The alpha gate is "Drive with desktop sync" and "no data loss for 30 days across all alpha servers".

The goal is to come as close as possible to Google Drive for desktop and Google's Drive app:

- **Files sit in Explorer and Finder** like any others. They download when they're opened, and folders can be kept on the computer for offline use.
- **Changes reach every device within seconds,** wherever the devices are.
- **Nobody turns a VPN on or off.** The apps work at home, at work, and on mobile data.
- **One app holds several accounts.** Sam, for example, uses the family's server at home and an employer's Accordion server at work. From home, Sam's laptop still syncs the work files, and at work it still syncs the family's. Google Drive for desktop does the same with a personal and a work account.

Some pieces exist already:

- **Core's storage** keeps the folder tree, versions, the trash, and file contents by SHA-256 hash ([decision 6](0006-file-storage.md)). Every item has an ID that doesn't change when it's renamed or moved.
- **Saves can be refused when the file changed underneath them.** `PUT /items/{id}/content` takes `If-Match` with the hash the editor started from, and `If-None-Match: *` makes a new file only if its name is free. The web app's text editor uses both.
- **Resumable uploads** (`POST /uploads`, then `PATCH` pieces, then `finish`), and downloads that can continue from where they stopped, with `Range`.
- **Live updates** ([decision 19](0019-live-updates.md)): a stream of hints at `/api/live`, which planned for a sync client to use.
- **Remote access** ([decision 21](0021-remote-access.md)): WireGuard in the server, with GotaTun and smoltcp, and a DNS record that tells devices where home is. It said Accordion's own apps would make their own keys and switch between home and away by themselves.
- **Sessions for apps** ([decision 3](0003-sessions-and-tokens.md)): a bearer token that lasts 180 days without use, from a sign-in in the system browser through OAuth 2.0 with PKCE. That sign-in isn't built yet. Decision 3 said it ships with the desktop app.
- **Sharing** ([decision 16](0016-sharing.md)): items shared with someone appear in their **Shared with me**, not in their own Drive.

What's missing is a way for a device to ask what changed. Today a client would have to walk every folder to find out.

This decision covers how devices sync, the desktop app, and what the phone apps will share with it. The phone apps' own decision covers their screens, camera-roll upload, and notifications while closed. Docs' decision covers merging documents edited offline.

## Decision drivers

1. **Nothing is lost.** Every saved change survives conflicts, crashes, dropped connections, a full disk, and weeks offline.
2. **It works like Google Drive.** Files sit in Explorer and Finder, download when they're opened, and sync within seconds.
3. **Every server, from anywhere.** One app syncs several accounts on several servers at once, at home, at work, or on mobile data, even with a work VPN or another VPN on.
4. **Nothing leaks.** A device learns only about items its person can open now.
5. **Nothing leaves the box.** No relay, push service, or account at another company.
6. **Small on a Raspberry Pi,** with every family member's devices syncing.
7. **One developer.** Reuse what exists, and what each operating system already offers.

## Options: how a device learns what changed

### Option A: WebDAV, with sync reports

Drive already serves WebDAV. [RFC 6578](https://www.rfc-editor.org/rfc/rfc6578) adds a sync report that lists what changed in a folder since a token.

Pros:

- **A standard,** so other clients could use it.
- **Mostly built.**

Cons:

- **WebDAV knows paths, not IDs.** A renamed or moved folder looks like everything in it was deleted and added again, so a client that follows it re-downloads the folder, and a conflict on a move can't be told from a delete.
- **Few file sync clients use sync reports.** It comes from calendars and contacts, so there's little to reuse.
- **No hashes in the standard,** so a client can't tell whether contents changed without downloading them.
- **XML,** which every client has to parse.

### Option B: A list of changes for each person

Core keeps a numbered list of what changed, for each person. A device remembers the last number it saw, and asks for everything after it: `GET /api/drive/sync/changes?after=<cursor>`. Each entry is the item as it is now, with its ID, folder, name, hash, size, and time, or "gone" if the person can't open it any more.

Pros:

- **Moves and renames are one entry,** since items keep their IDs.
- **Hashes come with each entry,** so a device downloads only contents it doesn't have.
- **Cheap to ask,** even after weeks offline (see the measurements).
- **Access is worked out when the change happens,** with the rule live updates already use, so the list can't name an item to someone who can't open it.

Cons:

- **New to build** in core, with a table that grows with every change and needs pruning.
- **Accordion's own protocol,** so third-party clients can't use it. WebDAV stays for them.

### Option C: Compare the whole tree

The device asks for the whole tree, or a hash for each folder so it can skip folders that didn't change, and compares it with what it has.

Pros:

- **No list of changes to keep** on the server.
- **Can't fall out of step,** since it always compares everything.

Cons:

- **Slow for big Drives.** A first sync of 40,000 items is a 10.5 MB list. Folder hashes help, but every change rewrites the hash of every folder above it.
- **Shared folders need a tree for each person,** since each one sees a different set of items.

## Options: how files appear on a computer

### Option 1: The operating system's cloud files

Windows has the Cloud Files API, which OneDrive and Google Drive use. macOS has File Provider, which Google Drive, Dropbox, and OneDrive use. Each shows a folder of placeholders. A file downloads when something opens it, and Explorer or Finder offers **Always keep on this device** and **Free up space** (or **Remove Download**).

Pros:

- **It looks and works like Google Drive,** because it's the same system feature.
- **On-demand files,** with status icons in Explorer and Finder.
- **The system handles opening a file that isn't downloaded yet,** and tells the app when files change.

Cons:

- **Different on each system.** The Windows side is in Rust, through the `windows` crate. File Provider needs an app extension written in Swift, which calls the shared Rust code.
- **File Provider needs a paid Apple Developer membership** to sign the extension and have the app notarized.
- **Linux has nothing like it.**

### Option 2: A plain folder

The app keeps a full copy of the folders someone chooses, as ordinary files.

Pros:

- **Works everywhere,** including Linux, network drives, and backup software.
- **The least to build.**

Cons:

- **No on-demand files.** Folders are either on the computer in full or not at all.

### Option 3: A virtual drive

A file system of Accordion's own, through FUSE on Linux, macFUSE on macOS, or WinFsp on Windows.

Pros:

- **On-demand files on Linux too.**

Cons:

- **Needs a driver installed,** which macOS makes harder every year.
- **Apps that open a slow file hang,** and the system can't show what's downloaded.
- **Not what Google Drive does** on Windows or macOS any more.

## Options: how apps reach a server away from home

### Option I: A tunnel inside the app

The app runs WireGuard itself, with the same GotaTun and smoltcp crates as the server's end, and sends only its own requests through it. Each account gets its own tunnel.

Pros:

- **Several servers at once.** Sam's laptop has a tunnel to home and one to work, open together.
- **No clash with other VPNs.** Phones allow one system VPN at a time, so a work VPN or ProtonVPN would otherwise lock Accordion out. A tunnel inside the app isn't a system VPN.
- **No clash between private addresses.** Two servers can both be `192.168.1.20` on their own networks. The app picks the tunnel by account, not by address, so it never mixes them up.
- **No VPN permission prompt,** no admin rights on Windows or macOS, and nothing to turn on or off.

Cons:

- **Carries only the app's own requests.** A browser away from home still needs the WireGuard app, as it does today.
- **On iPhone, transfers that carry on after the app closes** go through the system, which can't use the app's tunnel.

### Option II: The system VPN, set up by the app

The app sets up a system VPN: VpnService on Android, a Network Extension on iPhone and Mac, and WireGuardNT on Windows.

Pros:

- **The browser and every other app reach the server too.**
- **Works while the app is closed.**

Cons:

- **One system VPN at a time on phones,** so it fights a work VPN, another VPN, and a second Accordion server.
- **Two servers with the same private address can't both be reached.**
- **Needs a VPN permission prompt,** and on Windows, admin rights to install.

### Option III: The WireGuard app only

People keep using the WireGuard app with the QR code from Settings, as they do today.

Pros:

- **Already works.**

Cons:

- **Turning it on and off by hand,** which the goal rules out.
- **The same limits as option II,** since it is a system VPN.

## Measurements

On the development machine, with SQLite in WAL mode and Python's `sqlite3`: 200,000 items for five people, and 500,000 changes, each recorded for the item's owner and one person it's shared with. That's a 58 MB database.

| Task | Time |
|---|---|
| A device catching up on 1,000 changes | 2.9 ms |
| A device asking when nothing changed | Under 0.01 ms |
| Recording one change for five people | 0.03 ms |
| Listing 40,000 items for a first sync | 0.25 s, 10.5 MB of JSON, 3.4 MB compressed |

Changes are recorded in the same transaction as the change itself, so they add rows, not commits. A Raspberry Pi 5 is slower, so these figures join the Raspberry Pi measurements already planned.

## Recommendation

**A list of changes for each person (option B), cloud files on Windows and macOS with a plain folder on Linux (options 1 and 2), and a tunnel inside the app for each account (option I).** WebDAV stays for third-party clients. The WireGuard app stays for browsers away from home.

### The list of changes

- **Core's storage records a change** whenever an item is made, saved, renamed, moved, trashed, restored, or deleted for good, from any client: the web app, WebDAV, the sync apps, or a module.
- **Each change is recorded for each person it affects,** worked out when it commits, with the rule live updates use: the owner, and everyone the item or a folder above it is shared with. A move records the change for the people who could open the item before and after, so people who lose sight of it hear "gone".
- **Sharing records one entry for the shared item,** marked as a whole folder. Someone who gains access lists everything inside it. Someone who loses access hears that it's gone, with everything inside.
- **An entry is the item as it is now,** not what happened to it. If an item changed five times since the device last asked, the device gets it once.
- **The list comes in pages of up to 1,000,** each with the cursor for the next one.
- **Entries are kept for 90 days.** A device that's been away longer, or whose cursor the server doesn't know, such as after a restore from backup, is told to start over.
- **Names, hashes, and sizes are only sent for items the person can open now.** "Gone" carries only the ID.

### First sync and starting over

- **The device lists everything the person can open,** in pages, then follows the list of changes from the cursor it got before listing.
- **Starting over compares, it doesn't download.** A file whose local hash matches the server's is kept as it is. Anything that differs is treated as a conflict, never overwritten.

### Uploads and downloads

- **New files** use `If-None-Match: *`, so they never replace a file someone else just made with the same name.
- **Saves** use `If-Match` with the hash the device last synced, as the text editor does. Large files use resumable uploads, and `POST /uploads/{id}/finish` gains the same check.
- **Downloads continue where they stopped,** and the device checks the hash before it puts the file in place.
- **A copy made on the computer of a file already in Accordion** is copied on the server instead of uploaded again, if the person can open the original. The server never says whether it holds contents someone can't open, so nobody can test for a file they haven't seen.
- **Uploads and downloads can be limited** in Settings, and pause on connections Windows or the phone marks as metered unless the person allows them.
- **Whole files only.** Sending only the changed parts of a large file waits until it's needed.

### Conflicts

When two devices change the same thing before either syncs, the server's version keeps the name and nothing is thrown away:

| What happened | What Accordion does |
|---|---|
| The file was edited on two devices | Keeps both. The other copy is named like `Budget (conflict, Sam's laptop, November 4, 2026).xlsx` and goes next to it |
| Edited on one device, deleted on another | The edit wins, and the file comes back |
| A folder was deleted, and something new was saved inside it offline | The folder stays in the trash. The new files go into a folder with its name in the same place |
| Moved or renamed on two devices | The last one the server receives wins |
| Two new files with the same name | The second gets a number, like `Notes (2).md` |

- **A conflict sends a notification** to the bell, saying which file and where the copy went.
- **Older versions stay in the file's versions,** as they do for every save.
- **Docs and Notes merge edits** instead of making copies once their decisions are built, through the CRDT engine the spec plans for `accordion-sync`.

### Mistakes that look like deletes

- **A sync folder that disappears,** such as on a drive that's been unplugged, pauses sync. It's never read as "delete everything".
- **Deleting more than 100 items at once on the computer** pauses and asks before the deletes reach the server, as Google Drive does.
- **Deletes go to Accordion's trash,** where they stay for 30 days.

### Names the computer can't hold

Accordion allows names that Windows or macOS can't, such as `Report.pdf` and `report.pdf` in one folder, or `:` and `?` on Windows.

- **The device gives the file a local name,** such as `report (2).pdf` or `What next_.txt`, and remembers which item it is by ID.
- **The name on the server doesn't change,** unless someone renames the file on the computer.

### Files on each computer

- **Windows:** the Cloud Files API. Each account appears in Explorer's navigation pane, named like **Accordion (Home)**, with **My Drive** and **Shared with me** inside. Files download when opened. **Always keep on this device** and **Free up space** work from Explorer's menu.
- **macOS:** File Provider, with the same folders under **Locations** in Finder. The extension is in Swift and calls the shared Rust engine.
- **Linux:** a plain folder for each account, with the folders the person chooses kept in full. On-demand files on Linux wait until people ask for them.
- **Selective sync everywhere:** on Windows and macOS, a folder can be kept on the computer or left in Accordion. On Linux, a folder is synced or not.

### Shared items

- **Shared with me** shows items shared with the person, as in the web app.
- **Items someone can only view are read-only on the computer.** If one changes anyway, the change is kept as a copy in **My Drive**, and the app says so.
- **Moves follow the web app's rules.** If the server refuses one, such as moving another person's file out of their folder, the item goes back where it was, and the app says why.
- **Shortcuts to shared items in My Drive,** which are on the Drive roadmap, appear as folders on the computer once they're built.

### Several servers

- **The app holds several accounts,** on one server or many, and syncs them all at once.
- **Each account has its own folder, session, cursor, and tunnel.** Nothing is shared between them, so removing one leaves the others alone.
- **Each server's admin sees every device,** as today, and can remove any of them. Sam's employer's admin sees "Sam's laptop" in the list.

### Home and away

- **Each account remembers two ways to the server:** its address at home, and its tunnel.
- **When the network changes, the app tries both at once** and uses the first that completes a TLS handshake for the server's name. A different device at the same address on someone else's network can't pass the certificate check. Each new connection tries the way that worked last, and starts the other 300 ms later if the first hasn't finished, the way browsers try IPv6 and IPv4.
- **Through the tunnel, the app connects to the server's own address on the tunnel,** not its home address. Only the server answers there, and the app picks the tunnel by account, so two servers with the same addresses never mix.
- **At home, the direct way usually answers first.** Away, the tunnel does. For Sam at home, that means the family server directly and the work server through its tunnel.
- **The tunnel uses the same device list as decision 21.** The app makes its key on the device and registers only the public half, for its own session. The key works only while the session does, so signing the app out in **Where you're signed in** cuts it off at once. App keys aren't listed with the devices set up for the WireGuard apps, and don't count toward their 10.
- **The app registers its key again each time it starts,** so its setup follows the server's port, and it gets a tunnel if remote access was turned on since it was added.
- **A network that blocks the tunnel's UDP port** shows the account as unreachable, with a message that says the network may be blocking it. The other accounts carry on.

### Adding an account

- **At home,** the app asks for the server's name and signs in through the system browser, as decision 3 says. It then registers its tunnel key over that session.
- **Away from home, with a code from a signed-in device.** In **Apps and devices**, on the web or in an app that's already signed in, **Add the Accordion app** shows a short code to type. With remote access on, it also shows a QR code and the same setup as text to copy, for computers without a camera. It's good once, for 10 minutes, and needs a sign-in from the last 15 minutes, as other sensitive actions do.
- **The typed code works where the app reaches the server directly,** such as at home. It's too short to hold a tunnel's setup, which needs the server's public key. Away from home, the app needs the QR code or the copied setup.
- **The setup carries a temporary tunnel key** that only reaches the address for adding a device. The app uses it once to send its own public key and get its session. The server lets the key in while the code works, and for one minute after it's redeemed, so the answer gets back through the tunnel it came in. Its addresses come from the top of the tunnel's range and devices' from the bottom, so the new app never takes the address its temporary key just had.
- **So Sam can add the work account to the home laptop from home,** with the code from Sam's phone, which is already signed in to work.

### Staying up to date

- **The app keeps a live updates stream open for each account** while it's running. A `drive.items` or `drive.shared` hint starts a sync from the list of changes, and so does reconnecting.
- **Changes on the computer sync within a couple of seconds,** after the system says a file changed and it's been quiet for a moment, so a file still being written isn't sent halfway.
- **The device's state is kept in SQLite on the device.** A downloaded file is written to a temporary name, flushed, renamed into place, and only then recorded, so a crash at any point leaves either the old file or the new one.

### The desktop app

- **Built with Tauri, as the spec plans,** in `accordion-desktop`, over the shared engine in `accordion-sync`.
- **It lives in the system tray or menu bar,** showing what's syncing, any problems, and the accounts.
- **It updates itself** with releases signed by the same key as the server's ([decision 12](0012-updates.md)).

### What the phone apps share

- **The engine, the list of changes, conflicts, and the tunnel** are the same Rust code, called from Kotlin and Swift.
- **Phones keep files on demand,** with **Available offline** for files and folders to keep.
- **On Android, other apps open and save Accordion files** through the system file picker. On iPhone, Accordion appears in the Files app through File Provider.
- **The phone apps' decision covers the rest:** screens, camera-roll upload, and what to do on iPhone when the app is closed away from home.

### Security

- **Files on a computer aren't encrypted by Accordion.** The user guide asks people to turn on BitLocker or FileVault, and says why.
- **The session token and tunnel key sit in the system's keychain.**
- **A removed device stops syncing at once,** because its session and tunnel key stop working.
- **The list of changes needs a session,** like every other address, and names nothing a person can't open.

### Testing

- **Model tests for the engine,** in Drive's tests, so they run against Drive's real addresses instead of a simulated server. Three devices and the browser make random changes, devices sync in random order, requests fail (sometimes after the server did the work), and devices crash partway through a pass. At the end, every device matches the server, and every contents a device synced or the browser saved is in a file, a conflict copy, a version, or the trash. Each run repeats from its seed, CI runs a few short ones, and `ACCORDION_MODEL_SEEDS` and `ACCORDION_MODEL_STEPS` run more. Each bug they find also gets a test of its own.
- **Core's tests** check that the list of changes follows access exactly: shares made and removed, moves into and out of shared folders, the trash, deleting for good, and pruned cursors.
- **Drive's tests** check the sync addresses, the access test's list of every address, and the new check on finishing an upload.
- **The tunnel's tests** connect the app's tunnel to real servers in the test, in the suite's `tests/app_tunnel.rs`: two servers at once with the same home and tunnel addresses, adding both accounts through codes' temporary keys, a temporary key refused everywhere but the address that redeems it, signing out cutting off only that server's tunnel, and switching from the direct way to the tunnel when home stops answering.
- **Windows and macOS tests** run on GitHub's Windows and macOS runners.
- **A soak test on the Raspberry Pi** runs devices making random changes for days, which is how the alpha gate gets checked.

### Build order

1. **The server:** the list of changes in core, its addresses in Drive, the check on finishing an upload, sign-in for apps through OAuth with PKCE, and adding an app with a code. Sign-in through the browser was built on November 5, 2026: the app opens `/oauth/authorize`, the person allows it there, and the browser brings a code back to the app's own address on `127.0.0.1`. Codes work once, for 2 minutes, and only with the app's PKCE secret.
2. **The engine** in `accordion-sync`, with its model tests and a command-line client that syncs a plain folder. That's the Linux client, and the first one that works.
3. **The tunnel in the app,** with two servers at once. Built on November 5, 2026, for the command-line client.
4. **The Windows app,** with the Cloud Files API. Built on November 5, 2026, and in testing: each account is a sync root in File Explorer, files arrive as placeholders and download when opened, and the tray app adds accounts through the browser or with a code.
5. **The macOS app,** with File Provider.
6. **The phone apps,** after their own decision.

### Revisit this decision if

- Large files that change a little at a time, such as video projects or mail archives, turn out to be common. Sending only the changed parts would then be worth building.
- The list of changes grows too large for a Raspberry Pi, even with 90 days kept.
- Networks that block the tunnel's UDP port turn out to be common.
- Linux users ask for on-demand files.

## Consequences

- **Core's storage** gains the list of changes for each person, pruning after 90 days, and server-side copies by hash for items someone can open.
- **`accordion-sync`** gains the engine: the device's state, comparing local and server changes, conflicts, local names, and transfers.
- **Drive** gains `/api/drive/sync/` addresses, the `If-Match` check on finishing an upload, and conflict notifications.
- **The server** gains OAuth with PKCE for apps (decision 3), and adding an app with a code.
- **Core's identity** gains the temporary tunnel keys for adding an app, and apps' own tunnel keys, tied to their sessions.
- **The gateway's tunnel** lets temporary keys reach only the address for adding a device.
- **The web app** gains **Add the Accordion app** under **Apps and devices**.
- **New repos:** `accordion-desktop` for the Tauri app, created with `scripts/new-repo.sh`. The phone app repos come with their decision.
- **Releases** gain desktop app builds for Windows, macOS, and Linux, signed with the release key.
- **Core's license check allows CDLA-Permissive-2.0,** for Mozilla's root certificates in `webpki-root-certs`, which rustls-platform-verifier brings on Windows, macOS, and phones. It's a license for data that asks only that the license text comes with the data, so the apps list it with their other third-party notices. Settled on November 5, 2026.
- **Signing the apps** is [decision 24](0024-signing-the-apps.md): SignPath Foundation for Windows, and the Apple Developer Program for macOS. Settled on November 5, 2026.

## Open questions

- **The browser away from home.** The desktop app could carry the browser's requests through its tunnel too, so the WireGuard app isn't needed on a computer with Accordion installed.
- **A fallback for networks that block UDP,** such as the tunnel over TCP or HTTPS.
- **Removing a device's copies,** when a person or admin removes a device that later comes back online.
- **How long to keep the list of changes,** if 90 days proves too short or too long.
